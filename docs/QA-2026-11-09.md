## Why it is slow

Two causes add up on every request.

1. **The database checked permissions row by row (fixed).** Most read policies
   called `is_owner_of(trip_id)` / `is_kid_of` / `is_active_guest_of`. They are
   SECURITY DEFINER, so Postgres cannot inline them and runs a member lookup for
   **every row**. Permissive policies are ORed, so a guest reading photos also
   paid the owner and kid checks per row. 00059 (wall) and 00074 (options) had
   fixed this for a few tables; 41 tables were still in the old form.
   - Live `pg_stat_statements`: `itinerary_days` by trip averaged **372 ms**,
     `phrasebook_entries` **354 ms**.
   - Edge logs, 24h: most REST reads **250-550 ms at the origin**, p90 600-900 ms.
   - EXPLAIN as an owner: `select * from itinerary_days where trip_id = ...`
     **169 ms** with the old policies, **4 ms** with the new form (same 230 rows).
   - Realtime runs the same check for every subscriber on every change.
2. **Distance (not code, not fixed).** The Supabase project is in Frankfurt
   (eu-central-1). In the last 24h, 4,225 of 5,775 API requests came from
   Vietnam through Hong Kong. Every request pays the Asia-Europe round trip
   (X roughly 200-300 ms, an estimate; the logs record origin time only) on
   top of the database time. See "For Hadar" below.

## Found and fixed

| # | Severity | Finding | Fix |
|---|---|---|---|
| 1 | High (performance, every screen) | 41 tables' read policies evaluated the membership check once per row (see above). | **00086**: the same rules in 00059's once-per-query form (`trip_id = (select member_trip_as('owner'))` etc., `(select current_member_id())`, `(select auth.uid())`). USING of SELECT / FOR ALL policies, and a FOR ALL's WITH CHECK only where it is the same owner rule. INSERT/UPDATE/DELETE-only policies unchanged. Applied to production 09/11. |
| 2 | Low (performance) | Advisor: `members_self_select` re-evaluated `auth.uid()` per row; `fx_rates` (18k rows) ran `current_member_id()` per row. | Both in 00086. |
| 3 | Low (performance) | Advisor: two foreign keys without an index (`destination_facts.created_by`, `place_options.created_by`). | Indexes in 00086. |

**Same access, proven two ways:**
- *Before/after diff:* DB built at 00085, every public table seeded (the deny
  matrix seeder plus rows guests and kids may see), every identity's visible
  rows recorded (owner, kid, guest, revoked guest, outsider, anon, another
  family's parent), 00086 applied in the same transaction, recorded again:
  **0 rows gained or lost** in any table for any identity.
- *Probes:* new `86_rls_once_per_query_rest.sql` (13 checks: role access on the
  rewritten tables, rule 3, and a guard that fails if any SELECT/ALL policy
  calls a per-row helper again). Full suite **501 PASS, 0 FAIL**.
- *Live:* after the apply, 0 SELECT/ALL policies call a per-row helper or a
  bare `current_member_id()` / `auth.uid()`.
