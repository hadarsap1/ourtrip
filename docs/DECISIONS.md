# OurTrip - Locked Decisions

Decisions already made by Hadar & Sivan. Claude Code: do not reopen these; if implementation reveals a real blocker, raise it explicitly instead of silently deviating.

| # | Decision | Detail |
|---|---|---|
| 1 | PWA, not native | Installable web app; offline via SW + IndexedDB |
| 2 | Stack | Next.js + TypeScript + Tailwind + Supabase + Vercel |
| 3 | Roles | owner / kid / guest only, enforced by RLS |
| 4 | Kid photos need approval | Always. No setting to disable. Kid uploads force `pending` server-side |
| 5 | Guest sharing is opt-in per item | Nothing is guest-visible by default. For photos this means BOTH `status='approved'` AND `shared_with_guests=true` - approval alone never exposes a photo to guests, including owner uploads |
| 6 | Language | Hebrew RTL UI everywhere, incl. guest portal |
| 7 | Base currency | ILS; expenses keep original currency + conversion. FX provider: open.er-api.com / exchangerate.host (global coverage - the trip crosses many currency zones), Frankfurter as fallback, last-known-rate as final fallback |
| 8 | Out of scope | Memory book PDF, live flight tracking, email auto-extraction (backlog), multi-trip UI |
| 9 | Offline-critical set | Documents (flagged), today's itinerary, emergency page, phrasebook |
| 10 | Conflict policy | Last-write-wins + toast notification. Every editable table carries `updated_at` (trigger-maintained) |
| 11 | Photo size | Client-side compression ~1600px / ~300KB target |
| 12 | Pocket money | Informational; excluded from family budget totals |
| 13 | Cut order under pressure | Notifications → recommendations. Never security/backup |
| 14 | App name | ~~**OurTrip**~~ **"סו-בב עולם!"** since 14/10/2026 (Hadar): the brand became the whole app - home-screen name, icon (the family badge), tab titles, login. Technical identifiers (repo, IndexedDB names, passkey RP name, ICS PRODID) stay `ourtrip` so nothing on a device breaks. Was TripHub in early drafts; OurTrip from 2026-07-16 |
| 15 | ~~Messages = one shared family wall~~ **superseded 2026-08-29 (see #18)** | Was: owners + kids + guests all read/write the same feed. The 2026-08 security review (finding M5) flagged this as the only place anything reaches a guest - or reaches the kids *from* a guest - without a parent approving it first |
| 16 | Multi-country trip | Round-the-world route. Emergency page + phrasebook are per-country/per-language; weather + FX follow the itinerary day's location. Nothing assumes a single destination |
| 17 | Guest invite emails | Supabase built-in SMTP is rate-limited (~2/hour) and not production-safe - use custom SMTP (e.g. Resend free tier) for magic links from Sprint 7 |
| 18 | Messages = two feeds | `messages.channel`: **family** (owners + kids) and **guests** (owners + guests). Parents are in both and are the bridge; kids are kept out of the guest feed entirely, since a feed a child can read is a feed a child can be addressed in. Enforced by RLS, not the client - migration `00027`. Unread state still per member in `message_reads` |
| 19 | Options bank has two exits | An option reaches a day as an itinerary item (`planned`) or becomes a booking (`booked`). Booking-only was the reason 343 collected options never moved: you do not reserve a viewpoint. Areas are canonicalised so "how many options here, how many days here" is answerable - migrations `00029`/`00030` |
| 20 | Bookings reach the plan by date, not by hand | A booking is projected onto every date its own `start_date`/`end_date` covers - calendar grid, day cards and day strip - with no linking step. "Add to day" survives for the case it was actually good at (a booking that deserves a timed slot with a location), and a day already showing a booking as a linked item suppresses the projection there so nothing appears twice. Lodging covers its nights, not the morning of check-out; a cancelled booking is projected nowhere, since it is not happening. Pure client-side in `lib/bookingCalendar.ts` - no schema change, and `bookings` stays owner-only at the policy level |
| 21 | Booking confirmations come from the mailbox, not from the booking sites | Booking.com, Airbnb, Agoda and the airlines expose no API for reading your OWN reservations - their APIs are for partners selling inventory. Email is the one channel every provider uses, so one Gmail integration covers all of them. Supersedes the "out of scope" half of #8: `Email-forward booking extraction` moves out of the backlog and ships as `gmail-bookings` |
| 22 | The Gmail token is never stored | The owner's Google access token is obtained in the browser (GIS, `gmail.readonly`), passed to the Edge Function for one request, and dropped. No refresh token, no server-side mailbox credential, no row holding a key to a mailbox - same pattern as `gphotos`. The price is that scanning is a button rather than an overnight job, which is the trade that was chosen deliberately. Extraction proposes; the owner ticks what gets saved |
| 23 | One label per country in the options bank | The bank had drifted to two headings per country (ויטנאם/וייטנאם, פיליפינים/הפיליפינים) because country and area are free text with a datalist - a suggestion, not a constraint. `country_code` was correct on every row, so migration `00034` picks one label per ISO code (most-used wins, originals kept in `country_original`) and needs no judgement about Hebrew spelling. `canonicalLabel` then snaps new input onto a spelling the bank already holds, ignoring a leading ה, a doubled yod and a doubled vav; it can only ever return a label that already exists, so a genuinely new country still gets added as typed |
| 24 | A leg offers its own region's towns, not the whole country | `areaChoicesForCountry` filtered by country alone, so a trip crossing one country twice offered the same 25 towns both times - Saigon under "וייטנאם - צפון", Hanoi under "דרום ומרכז". `areaChoicesForStretch` reads the leg's label: a label naming towns in the bank puts those first and sorts the rest by distance (a base with day trips - nothing hidden); a label naming a direction cuts the country's own geocoded span into three bands and offers the named ones, with the rest behind a toggle. Neither matched, or a filter that keeps everything or nothing, falls back to the whole country. No destination is hardcoded (CLAUDE.md #9), and an area with no coordinates is always offered - a band is evidence, and there is none for an ungeocoded town |
| 25 | Sharing = stories + podcast, WhatsApp is the doorbell | Decided 13/10/2026 (docs/DESIGN-sharing.md). The app holds the content - a blog of stories and the kids' podcast - and a parent sends one prepared line with a link to whichever WhatsApp group they choose (phone share sheet / wa.me). No WhatsApp API, no stored groups. Brand: "סו-בב עולם!" (the hyphen is the family name), the farewell-invitation illustration, Gveret Levin for display type. Since 14/10/2026 the whole app wears it (Hadar): the core tokens carry parchment / ink / sage in light and dark, every screen title is in Gveret Levin except the emergency page, which stays plain for legibility. One system, no second look for the sharing screens: the handwriting is for screen titles and the wordmark only; card titles, section headings and numbers are Heebo; one card and one button style everywhere (14/10, after Hadar saw the stories screen differ) |
| 26 | A story has one audience and one gate | `posts.visibility` family / guests / public, `posts.status` draft / pending / approved (00043). Kids write and send for approval; `posts_guard` keeps audience, approval and publish time out of their hands. A story never widens a photo: guests see only the story's photos that are themselves approved AND shared (DECISIONS #5 unchanged); the publish sheet offers to approve+share them as an explicit parent action |
| 27 | The open blog is copies, owner-authored only | Visibility `public` exists for a parent's own story only - a kid's story can never be public, enforced in `posts_guard` for every role. Its photos are copied to a separate public bucket at publish and deleted at unpublish; the private `photos` bucket is never made public and anon has no policy on `photos` or `members`. Public pages are noindex and carry no comments or likes (00046). Faces of the kids in a public story are each parent's call per story (13/10) |
| 28 | Podcast = the photo rules, never public | `episodes` (00044): kid recordings land pending and unshared whatever is sent; approval and sharing are two parent steps; un-approving un-shares. Guests hear an episode through short-lived signed URLs from `guest-media` after their own RLS returns it. No anon policy, private bucket |
| 29 | Every guest sees every guest item; labels are for addressing | Classes, family and friends are all ordinary guests (13/10). `guests_allowlist.label` groups the list for managing and inviting; no policy reads it. Per-group scoping was considered and not built |
| 30 | The bridge is approved, and covers comments | DESIGN-wall-bridge approved 13/10, extended to comments: kids have no policy on `comments` at all; a parent copies one comment or message across the feeds as a new row in the author's name (00045). Kids see likes with names - a like is not a channel anyone can write words into, so #18 holds |
| 31 | Parents edit episodes on the device, saved as WAV | 13/10/2026. Keep / cut a marked part, add a take or another episode at the end, rename, undo (lib/audioEdit.ts). The browser can decode every recorded format but cannot encode a compressed file without a muxing library, so the edit is saved as 16 kHz mono 16-bit WAV (~1.9 MB/min, plays everywhere). Episodes run up to 20 minutes (raised from 7 on 13/10): ~38 MB edited, so the audio bucket allows 50 MB per file. Replacing the audio is owner-only; editing keeps approval and sharing (00047) |
| 32 | The journal is the family's own; stories are what goes out | Hadar 14/10/2026: the guest-readable journal and the stories were two places telling guests the same day. The journal stays the family's diary - owners and kids, the kids' daily prompt ("מה היה הכי כיף היום?"), the memory book - and guests have no policy on it. An entry reaches guests only by becoming a story ("הפיכה לסיפור"), through the story's audience and approval. Migration `00048` drops the guest policy and the `shared_with_guests` column, so there is nothing to tick by mistake. Photos attached to an entry still follow #5 on their own |
| 33 | One wall: friends, family and the kids; a kid's message waits for a parent | Hadar 14/10/2026: the family is together all day, so the family feed goes; the kids write to friends and family instead. Supersedes the "kids never read the guest feed" half of #18 and the bridge of #30. Kids read the approved wall, guests included; a kid's message is held (`messages.approved_at` null) until a parent approves it, and guests never see it before - forced by a trigger whatever the client sends (00049). The other half of #18 stands: nothing from a kid reaches a guest without a parent |
| 34 | Parents record the podcast; kids listen and read the listeners | Hadar 14/10/2026: "they'll just play with it". Kids have no insert/update/delete policy on `episodes` and cannot upload audio. They hear approved episodes and read the comments, read-only (`comments_kid_select`): on episodes since 00049, and on stories too since 00050 (Hadar 14/10). Amends #28 |
| 35 | Documents are owner-only; pocket money hidden | Hadar 14/10/2026. The B1 "share a document with the kids" (00014) is removed with its column and policies - 0 documents were shared (00049). Pocket money stays in the database but its screens are hidden behind the `pocketMoney` flag until the family decides to use it |
| 36 | AI has a monthly budget, and booking import runs on Sonnet | Hadar 14/10/2026: "so I don't get an inflated bill by mistake". Every function that calls the Claude API reserves first (`ai_reserve`, 00053): refused when this month's estimated spend has reached the trip's budget ($10 default, a parent changes it in settings, 0-200) or when the trip hit that function's daily cap; it fails closed. After the call the function records its real tokens and estimated cost (`ai_record`, service role only). No usage meter in the UI, by choice. `gmail-bookings` and `booking-paste` move from Opus 5 to Sonnet 5.5 (~2.5x cheaper; the owner reviews every candidate; paste moved on Hadar's yes, 14/10). The Anthropic Console spend limit stays the hard backstop |
| 37 | Guests join through one link, a parent approves each one | Hadar 15/10/2026: collecting addresses on WhatsApp and typing them in was too much friction. One join link per trip (`guest_join_links`, 00054), posted in any group; whoever opens it asks with Google (one tap, verified address) or a typed name and address. Every request waits for a parent (manual approval for everyone, no auto-approve); approval is the existing `guest-invite` call, so the request itself grants nothing. No expiry; a parent can reset the link, which kills the old one. The person enters their own address, so nobody is put on the list who did not ask. Manual and list invites stay as they were |
| 38 | Podcast pauses shorten on the device; a locked screen pauses, never loses | Hadar 17/10/2026: shorten silences rather than remove them, no AI or transcription service for now (it would need a new external API outside the locked stack). Long pauses become 0.5 s (`shortenSilences`, lib/audioEdit.ts). The recorder holds a Screen Wake Lock; when the page is hidden it closes the current part and pauses, and resume opens a new microphone part - parts are joined into one WAV on stop. A web app cannot record with the screen off; this keeps what was recorded |
| 39 | Wall, stories and photos can go to guest groups | Hadar 22/10/2026: Omer writes to his class only, and something else to everyone. Supersedes "every guest sees the same content" (decided 13/10, DESIGN-sharing question 2). `audience text[]` on `messages`, `posts` and `photos` (00063): `{}` = everyone as before, otherwise only guests in one of those groups (`guests_allowlist.labels`, 00061). A group can belong to a kid (`guest_group_kids`): that kid sees the group; Ella does not see Omer's class and the other way round; parents see everything. The wall gets one tab per group, and what is written in a tab stays in that group - a guest can only write to their own groups, a kid only to theirs, so a class's replies stay in the class. A kid's message still waits for a parent, who can change its audience before approving. Stories: the parent chooses groups when publishing to guests (kids never set an audience). Photos: the audience narrows #5, never widens it - approved AND shared AND in the guest's group; sharing a group story's photos limits them to that group, and never narrows a photo already shared with everyone. Kids keep seeing every family photo. Push previews follow the same rule (`_shared/wallAudience.ts`) |
| 40 | Group audiences, simplified: the family sees everything | Hadar 22/10/2026, amends #39: "the group belongs to a kid" was confusing. Now only: a guest is in one or more groups, given when a parent approves the join request (or later); whoever writes or uploads - parent, kid or guest - chooses everyone (default) or one or more groups, a guest only from their own; group content is seen and answered only by guests in those groups; parents AND kids see everything (00064 drops `guest_group_kids`). A kid's message, story or photo carries the kid's choice and still waits for a parent, who can change it. A photo uploaded for some groups stays there - sharing it in a story for everyone does not open it wider |
| 41 | The wall is one feed with replies; a reply goes where its message went | Hadar 22/10/2026, amends #39/#40: group tabs confused guests - one answering a class message from the "everyone" tab sent the answer to everyone. No tabs: everyone sees one feed of what they may read, a group message marked "רק ל: ...". Every message has "תשובה"; a reply sits under its message and always gets that message's audience (`messages.reply_to`, forced by `messages_reply_guard`, 00066), so guests never choose a group. A guest's new message goes to everyone; the family can pick groups for a new message. A new reply brings its conversation to the bottom of the wall |
| 42 | A guest can carry the kids they are a parent of | Hadar 23/10/2026: most class guests are a parent who joined with their own address, since the kid has none. `members.kid_names` (00067), up to three names, shown as a small "של יואב" tag next to the name on the wall, in story comments and likes, and in the guest list and join requests. Typed on the join form (optional, carried over on approval), edited by the guest in settings (reached from their home), or by a parent from the guest list. Display only: no policy reads it, it changes nothing about who sees what. A guest edits it only through `set_my_kid_names`, which writes that one column of their own row; guests still have no UPDATE on `members` |
| 43 | Parents can view as a guest or a kid, in a real session | Hadar 23/10/2026: to check that every feature and flow works for the other roles. A UI-only switch would still read with the parent's rights and show what a guest never sees, so "view as" signs the phone into a real session of the trip's test guest or test kid (`members.is_preview`, 00068), minted by the `preview-session` Edge Function (parents only). The parent picks the test guest's groups on every entry. Writing is allowed and real, under the "🧪 אורח בדיקה" / "🧪 ילד בדיקה" names; a parent deletes it like any message. The parent's session is kept aside on the device and restored by "חזרה להורה" in a banner shown on every screen; the test session is signed out everywhere on the way back. Test members are hidden from the kids, devices and guests lists and from the checklist assignee picker. The device's screen caches are kept apart while viewing, so the parent's copies neither show nor get overwritten |
