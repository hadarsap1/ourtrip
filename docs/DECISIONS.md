# OurTrip - Locked Decisions

Decisions already made by Hadar & Sivan. Claude Code: do not reopen these; if implementation reveals a real blocker, raise it explicitly instead of silently deviating.

| # | Decision | Detail |
|---|---|---|
| 1 | PWA, not native | Installable web app; offline via SW + IndexedDB |
| 2 | Stack | Next.js + TypeScript + Tailwind + Supabase + Vercel |
| 3 | Roles | owner / kid / guest only, enforced by RLS |
| 4 | Kid photos need approval | Always. No setting to disable. Kid uploads force `pending` server-side |
| 5 | Guest sharing is opt-in per item | Nothing is guest-visible by default. For photos this means BOTH `status='approved'` AND `shared_with_guests=true` - approval alone never exposes a photo to guests, including owner uploads |
| 6 | Language | Hebrew RTL UI everywhere, incl. guest portal |
| 7 | Base currency | ILS; expenses keep original currency + conversion. FX provider: open.er-api.com / exchangerate.host (global coverage - the trip crosses many currency zones), Frankfurter as fallback, last-known-rate as final fallback |
| 8 | Out of scope | Memory book PDF, live flight tracking, email auto-extraction (backlog), multi-trip UI |
| 9 | Offline-critical set | Documents (flagged), today's itinerary, emergency page, phrasebook |
| 10 | Conflict policy | Last-write-wins + toast notification. Every editable table carries `updated_at` (trigger-maintained) |
| 11 | Photo size | Client-side compression ~1600px / ~300KB target |
| 12 | Pocket money | Informational; excluded from family budget totals |
| 13 | Cut order under pressure | Notifications → recommendations. Never security/backup |
| 14 | App name | **OurTrip** (was TripHub in early drafts; renamed 2026-07-16) |
| 15 | ~~Messages = one shared family wall~~ **superseded 2026-08-29 (see #18)** | Was: owners + kids + guests all read/write the same feed. The 2026-08 security review (finding M5) flagged this as the only place anything reaches a guest - or reaches the kids *from* a guest - without a parent approving it first |
| 16 | Multi-country trip | Round-the-world route. Emergency page + phrasebook are per-country/per-language; weather + FX follow the itinerary day's location. Nothing assumes a single destination |
| 17 | Guest invite emails | Supabase built-in SMTP is rate-limited (~2/hour) and not production-safe - use custom SMTP (e.g. Resend free tier) for magic links from Sprint 7 |
| 18 | Messages = two feeds | `messages.channel`: **family** (owners + kids) and **guests** (owners + guests). Parents are in both and are the bridge; kids are kept out of the guest feed entirely, since a feed a child can read is a feed a child can be addressed in. Enforced by RLS, not the client - migration `00027`. Unread state still per member in `message_reads` |
| 19 | Options bank has two exits | An option reaches a day as an itinerary item (`planned`) or becomes a booking (`booked`). Booking-only was the reason 343 collected options never moved: you do not reserve a viewpoint. Areas are canonicalised so "how many options here, how many days here" is answerable - migrations `00029`/`00030` |
| 20 | Bookings reach the plan by date, not by hand | A booking is projected onto every date its own `start_date`/`end_date` covers - calendar grid, day cards and day strip - with no linking step. "Add to day" survives for the case it was actually good at (a booking that deserves a timed slot with a location), and a day already showing a booking as a linked item suppresses the projection there so nothing appears twice. Lodging covers its nights, not the morning of check-out; a cancelled booking is projected nowhere, since it is not happening. Pure client-side in `lib/bookingCalendar.ts` - no schema change, and `bookings` stays owner-only at the policy level |
| 21 | Booking confirmations come from the mailbox, not from the booking sites | Booking.com, Airbnb, Agoda and the airlines expose no API for reading your OWN reservations - their APIs are for partners selling inventory. Email is the one channel every provider uses, so one Gmail integration covers all of them. Supersedes the "out of scope" half of #8: `Email-forward booking extraction` moves out of the backlog and ships as `gmail-bookings` |
| 22 | The Gmail token is never stored | The owner's Google access token is obtained in the browser (GIS, `gmail.readonly`), passed to the Edge Function for one request, and dropped. No refresh token, no server-side mailbox credential, no row holding a key to a mailbox - same pattern as `gphotos`. The price is that scanning is a button rather than an overnight job, which is the trade that was chosen deliberately. Extraction proposes; the owner ticks what gets saved |
| 23 | One label per country in the options bank | The bank had drifted to two headings per country (ויטנאם/וייטנאם, פיליפינים/הפיליפינים) because country and area are free text with a datalist - a suggestion, not a constraint. `country_code` was correct on every row, so migration `00034` picks one label per ISO code (most-used wins, originals kept in `country_original`) and needs no judgement about Hebrew spelling. `canonicalLabel` then snaps new input onto a spelling the bank already holds, ignoring a leading ה, a doubled yod and a doubled vav; it can only ever return a label that already exists, so a genuinely new country still gets added as typed |
| 24 | A leg offers its own region's towns, not the whole country | `areaChoicesForCountry` filtered by country alone, so a trip crossing one country twice offered the same 25 towns both times - Saigon under "וייטנאם - צפון", Hanoi under "דרום ומרכז". `areaChoicesForStretch` reads the leg's label: a label naming towns in the bank puts those first and sorts the rest by distance (a base with day trips - nothing hidden); a label naming a direction cuts the country's own geocoded span into three bands and offers the named ones, with the rest behind a toggle. Neither matched, or a filter that keeps everything or nothing, falls back to the whole country. No destination is hardcoded (CLAUDE.md #9), and an area with no coordinates is always offered - a band is evidence, and there is none for an ungeocoded town |
