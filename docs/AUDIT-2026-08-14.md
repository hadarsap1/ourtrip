# OurTrip — Pre-Departure Audit (2026-08-14)

Full e2e QA, privacy pass, and UX review against commit `1e99422`.

**Method.** The 18 migrations and 12 Edge Functions were read directly rather than trusting
`SECURITY-CHECKS.md`; `npm run build`, `tsc --noEmit`, `eslint`, `vitest`, and `playwright` were
executed; all 22 screens reviewed for role handling, offline behaviour, and RTL. No live Supabase
queries were run — the role matrix below is derived from policy source, and the production
verification in `SECURITY-CHECKS.md` (2026-07-27) still stands for everything it covers.

## Verdict

Every automated gate is green, and the server-side privacy model is genuinely strong: **no path was
found for a kid or guest to read documents, budget, bookings, or an unshared photo.** The real gaps
are on the client and in the spec's own unfinished corners — there is **no way to sign out of the
app**, guests can read the whole family's email addresses, and offline writes outside the budget
screen are silently lost.

## Verified correct

- Deny-by-default RLS on every table; kids and guests have **no** policy at all on `documents`,
  `expenses`, `bookings`, `budget_categories`, `saved_links`, `saved_recommendations`.
- The two-flag photo rule is enforced by triggers, not the UI: `photos_enforce_kid_rules` forces kid
  uploads to `pending` + unshared on insert, `photos_guard_update` freezes those columns on update.
  A hand-crafted request claiming `status='approved'` still lands as pending.
- All six storage buckets are private. Guests never touch `photos` / `gphotos` directly — the
  `guest-photos` / `guest-gphotos` functions list rows through the **caller's** JWT, so RLS decides
  what exists before any signed URL is minted.
- `is_active_guest_of()` re-checks `guests_allowlist.revoked_at` on every query → revocation is
  immediate, not eventual.
- Owner gates on `travel-search`, `recommend`, `emergency-autofill`, `gphotos`, `guest-invite`, and
  `kid-auth create-registration` re-check the role in-function, not just via `verify_jwt`.
- The document lock is real E2E encryption: PBKDF2-SHA256 @ 210k → AES-GCM-256, encrypted
  client-side before upload, key in memory only, never persisted.

## Privacy & security findings

### P-1 · High — There is no sign-out anywhere in the app

`supabase.auth.signOut()` is called in exactly one place — `AuthGate`, when it rejects an unknown
account. `strings.settings.signOut` ("יציאה") exists at `lib/strings.ts:719` but is never rendered.

SPEC §2.5 requires the opposite in writing: offline documents are cached unencrypted because
"device-level security assumed", *"but wipe on logout"*. Logout does not exist, so nothing is ever
wiped. A lost phone keeps a live owner session on a long-lived refresh token, plus the IndexedDB
copies of every offline-flagged document, today's itinerary, all emergency pages, and the map
snapshot.

**Fix.** Sign-out row at the bottom of `/more` running the full wipe: `signOut()` → `lockVault()` →
`clearKidDevice()` → delete all six IndexedDB stores → drop `ourtrip-docpin-*` and weather keys from
localStorage → `caches.delete()` the shell. Confirm first — wiping offline documents is destructive.

### P-2 · Medium — Guests can read every family member's email address

`members_kid_guest_select` (00008) grants kids and active guests `SELECT` on *all* `members` rows of
the trip so the wall can resolve sender names, and `listMembers()` (`lib/data/trip.ts:28`) issues
`select("*")` — which returns `email` and `auth_user_id`. Any invited guest can list both owners'
emails, the kid rows, and **every other guest's email address**.

The role-access matrix counted rows per role, not columns, which is why this passed. RLS is
row-level and cannot fix it alone.

**Fix (in the DB, per hard rule #1).** `REVOKE SELECT (email, auth_user_id) ON members FROM
authenticated`, expose names via a `security_invoker` view (`id, trip_id, display_name, role`), point
the wall and nav at it, and keep owner access through a separate grant.

### P-3 · Medium — Owner-only screens render fully for kids and guests

`/budget`, `/documents`, `/itinerary`, `/checklists`, `/guests`, `/kids`, `/notifications` have no
role guard. A guest gets a fully rendered budget dashboard reading ₪0 across every category, and a
Documents vault with a working-looking upload button. No data leaks (RLS returns zero rows, writes
are rejected), but an empty budget screen is indistinguishable from a real one showing zero spend.

`/recommend`, `/links`, `/memory-book` already do this correctly.

**Fix.** Apply the existing `RecommendScreen` guard pattern to the seven unguarded screens.

### P-4 · Medium — Every guest and kid sees the owner tab bar on first paint

`BottomNav` resolves role as `member?.role ?? (isKidDevice() ? "kid" : "owner")`. Until the async
`useMember()` lookup returns, `member` is `null`, so a guest on a slow connection is shown the full
owner navigation — Budget, Documents, Itinerary — and can tap into it before it swaps. Cosmetic in
intent, but it is precisely what makes a family member believe the app leaked their documents.
`useMember()` already returns `memberLoading`; nothing uses it.

**Fix.** Render a skeleton while `memberLoading`, and default the fallback role to the *least*
privileged tab set.

### P-5 · Low — Edge Function `verify_jwt` settings live only in code comments

There is no `supabase/config.toml`. Four functions deliberately run unauthenticated (`kid-auth`,
`fx-daily`, `push-send`, `backup-weekly`) and eight require a JWT — a split currently documented in
header comments and configured by hand in the dashboard. A redeploy from a clean checkout can
silently flip any of them.

**Fix.** Commit `supabase/config.toml` with explicit `[functions.<name>] verify_jwt = true|false`
for all twelve.

### P-6 · Low — Backups accumulate forever and restore has never been tested

`backup-weekly` dumps 26 tables into the `backups` bucket weekly, including `kid_devices` (PIN and
device-token hashes) and `push_subscriptions`. Bucket reads are correctly owner-only. Nothing prunes
old snapshots, and there is no documented restore path — so the one thing the roadmap calls "never
cut" is unverified.

**Fix.** Retention (keep last 8), plus one restore drill into a Supabase branch before departure,
logged in `SECURITY-CHECKS.md`.

### P-7 · Consider — Two deliberate decisions worth re-confirming

- **The family wall has no private channel.** DECISIONS #15 makes it one shared feed: every message
  the kids or the owners post is readable by every invited guest, forever. Documented intent — worth
  a conscious yes before the first guest link goes out.
- **The Documents PIN is the entire defense for locked documents.** Salt and verifier sit in
  `localStorage` and in an owner-readable row, so someone holding an unlocked device can brute-force
  the PIN offline against the verifier. At 210k PBKDF2 iterations a 6-digit PIN is hours of GPU
  work; 8+ digits pushes it out of reach. `DocPinSheet` accepts 6–12 — consider nudging toward 8.

## Unfinished spec commitments

### S-1 · High — Offline writes are queued for expenses only (SPEC §3)

`lib/offline/queue.ts` handles exactly one write kind: `"expense"`. Its replay logic is good — it
classifies transient vs. permanent failures so one bad entry never strands the queue — but it is the
only thing wired in.

Tick a packing-list item, write a journal entry, mark an itinerary item done, or log pocket money
with no signal, and the Supabase call throws. The screens catch it and show `strings.common.error`.
The write is gone, and nothing tells the person to retry. Journal entries written on a plane are
exactly the content most likely to hit this.

**Fix.** Widen `PendingWrite["kind"]` to cover journal entries, checklist toggles, pocket-money
lines, and itinerary status changes; replace the generic error toast on those paths with an honest
"saved, will sync when you're back online".

### S-2 · Medium — Emergency is not one tap from every screen (SPEC §2.12)

The spec asks for a persistent icon, "reachable in one tap from any screen". The 🆘 button exists on
the owner Today header, the kid home header, and as a row in `/more`. From Budget, Itinerary,
Documents, Map, Photos, or Journal it is two or three taps. The offline half is solid — all
countries are cached and `EmergencyScreen` renders from cache even when the trip row can't load.

**Fix.** Promote it to the app shell: a small fixed 🆘 in `app/layout.tsx` above the bottom nav,
hidden only on `/emergency` and the login screens.

### S-3 · Medium — The concurrent-edit warning was never built (SPEC §3)

The spec specifies last-write-wins *plus* a toast when the server version changed since read:
"עודכן גם ממכשיר אחר - בדקו את הפריט". That string does not exist in `lib/strings.ts`, and no code
path compares `updated_at` before writing. Every table carries the column and a maintaining trigger —
the data is there, the check is not. With two owners planning in parallel, one edit silently
overwrites the other.

**Fix.** Send the row's `updated_at` as a guard on owner-facing updates; on zero rows returned,
refetch and raise the Hebrew toast the spec already wrote.

### S-4 · Low — Four routes missing from the offline shell cache

`SHELL_URLS` in `public/sw.js` precaches 17 routes but omits `/guests`, `/kids`, `/login`,
`/kid-login`. Most relevant for `/kid-login`: the kid tablet's PIN screen is not precached, and PIN
unlock needs the network anyway — so a kid on a plane with a restarted tablet is locked out.

**Fix.** Add the four routes and bump `CACHE_NAME`. Separately, decide whether kid PIN unlock should
have an offline path at all; right now it does not, and that is not written down anywhere.

## Test coverage

### Q-1 · Medium — The e2e suite proves routes mount, and nothing else — and CI never runs it

All 26 Playwright tests pass at 390px, but they boot the app with **no Supabase environment wired
up**, which makes `AuthGate` bypass entirely. They verify the Hebrew RTL shell renders, the bottom
nav works, and no route throws. Zero data flows, zero role behaviour, zero offline behaviour, zero
realtime.

`playwright.auth.config.ts` and `e2e/authenticated.spec.ts` exist for the real thing, but
`.github/workflows/ci.yml` runs only `lint`, `test`, `build` — neither Playwright config runs in CI.
The definition-of-done items that say "verified" are verified by hand, once, and can regress
silently.

**Fix.** Add `npm run test:e2e` to CI, and grow the authenticated suite to cover the three claims
most likely to break: a guest session sees nothing on `/budget`, an offline document opens with the
network disabled, and a kid upload lands as `pending`.

## Missing for the trip itself

### M-1 · Critical gap — Documents have no expiry date, so nothing can warn you

The vault tags documents `passport` / `insurance` / `vaccine` / `visa` / `other`, but the `documents`
table has no expiry column and no screen surfaces one. Every date that can strand this family is
untracked:

- Most countries refuse entry on a passport with under six months of validity remaining, and
  children's passports are issued for shorter terms than adults' — four passports, four different
  expiry dates, on a trip crossing many borders.
- Visas have entry windows.
- Travel insurance ends on a fixed date and is the thing you discover has lapsed at a hospital.
- Migration 00018 notes the family has further vaccination rounds ahead, so some certificates aren't
  even issued yet.

The delivery infrastructure already exists and works: `handleDaily()` in `push-send` already computes
a flight check-in reminder from tomorrow's bookings. Adding a second query is small; the missing
piece is the column and the UI.

**Fix.** Add `expires_on date` to `documents`, surface it in the form and as a badge in the vault
list (red under 6 months for passports, under 30 days otherwise), and extend `handleDaily()` to warn
at 180 / 90 / 30 days. Owner-only, so `documents_owner_all` already covers it — no new policy needed.
